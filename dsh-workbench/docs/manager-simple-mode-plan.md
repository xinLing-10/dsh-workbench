# 管家简洁模式：实现方案

状态：待实施的设计方案，不代表当前界面已经具备这些功能。基于 `personal_manager` / 1.14.1，2026-11-13。

## 1. 要解决的问题与最终体验

当前管家把对话、任务状态、文档、审阅确认、模板和来源检查同时展示。普通用户难以判断现在轮到谁做事，以及应该点哪一个按钮。

简洁模式默认只展示三件事：

1. 一个持续对话入口：“你想做什么，或者哪里需要调整？”
2. 一张“现在需要你做什么”卡：解释当前结果、下一步和原因。
3. 一个主要操作按钮：回答问题、同意执行、查看成果或下载，随真实状态变化。

完整文档仍是主要交付物。简洁模式是现有管家的另一种呈现方式，复用原有任务、确认和交付记录；不增加一个新的执行 Agent，也不另建任务状态机。

桌面结构示意：

```text
小店预约                       使用手册 · 更多
正在准备需求文档

┌ 现在需要你做什么 ───────────────────┐
│ 请先看看预约规则是否符合你的想法     │
│ 重点：预约人数、取消方式、在线支付   │
│                   [查看并确认成果]  │
└────────────────────────────────────┘

你和管家的对话
[刚才的结果与必要说明……]
[告诉我你的想法或修改要求……] [发送]

[我的成果（3）]  [历史记录]
```

窄屏采用相同顺序的单列。当前动作卡不遮挡对话或文档；“停止”和“查看权限”在相关任务状态下保持可见，不能收到难以找到的菜单里。

## 2. 信息分层

| 层级 | 默认显示 | 进入方式 |
| --- | --- | --- |
| 日常操作 | 对话、当前动作、简短进度、成果数量 | 默认首页 |
| 成果操作 | 完整文档、修改意见、当前版本确认、直接下载 | 查看成果 / 我的成果 |
| 高级操作 | 模板、来源映射、历史版本、知识、阶段和队列 | 更多 → 高级选项 / 详细工作区 |

不删除现有能力。新用户默认进入简洁模式；熟悉工作台的人可切回“完整管家”或“详细工作区”。旧项目原地打开，模式切换只改变布局，不重新配置交付目标、不创建会话。

## 3. 当前动作由服务端给出

在 `manager.js` 的 `view()` 中增加只读 `presentation`，由独立的纯函数 `deriveManagerPresentation()` 生成。输入使用 Host 已持有的约定、任务状态、回答记录、文档确认和交付状态；前端不根据模型文案推测进度。

建议返回结构：

```json
{
  "schemaVersion": 1,
  "phase": "needs_review",
  "title": "需求文档准备好了，请你看看",
  "description": "重点核对预约人数、取消规则和本轮范围。",
  "primaryAction": { "kind": "open_review", "stage": "spec", "label": "查看并确认成果", "enabled": true },
  "secondaryActions": [{ "kind": "request_revision", "label": "我想修改" }],
  "blockingReasons": [],
  "relatedJobId": null,
  "relatedQuestionId": null,
  "revision": 12
}
```

其中标题、按钮标签和阻断条件使用确定性模板；模型只能提供补充解释，不能指定接口、URL、工具或下一阶段。`kind`、阶段、任务与问题标识均为枚举或当前项目中已经存在的标识。

### 3.1 状态与按钮

| 内部呈现状态 | 面向用户的表达 | 主要按钮 | 行为 |
| --- | --- | --- | --- |
| welcome | 先告诉我你想完成什么 | 请管家接下项目 | 建立明确的交付约定 |
| needs_info | 有一件事想请你决定 | 提交回答 | 复用 `answer`，不启动执行 |
| ready_to_start | 这次准备这样做 | 同意并开始 | 复用 `dispatch`，绑定当前 proposal ID |
| working | 管家正在准备 | 查看进展 | 展开真实步骤；旁边保留停止入口 |
| waiting_permission | 这一步需要你授权 | 查看授权详情 | 打开当前原生会话，不能代替授权 |
| needs_review | 成果准备好了，请你看看 | 查看并确认成果 | 打开审阅页，不直接提交 `approve` |
| needs_recovery | 工作暂时停下，需要处理 | 按原因显示重新连接 / 核对状态 / 查看记录 | 不盲目重发任务 |
| ready_to_download | 约定成果已确认，可以拿走了 | 下载文档 / 整理文档包 | 基于实际文件和确认记录提供可用操作 |
| idle | 还想补充什么？ | 发送消息 | 继续沟通，不自动推断执行授权 |

### 3.2 冲突时的优先级

1. 网络、服务不可用或任务 `uncertain`：先恢复或核对。
2. 正在停止、确有待授权信号或存在活动任务：展示相应状态，禁止重复开始。
3. 当前阶段的有效未回答问题：一次只显示一个问题，可说明还有多少问题。
4. 当前阶段待审阅成果：先引导审阅。
5. 当前阶段有效执行建议：等待用户同意。
6. 已满足交付约定：提供可用下载入口。
7. 否则继续沟通。

失败任务不应盖住后来已经成功的任务，历史问题也不能挡住当前阶段。判定只看当前轮次和相关最新任务。缺少应交付文档时显示“还需要补充内容”，不能提供会通过不了检查的确认按钮。

`waiting_permission` 只能来自可靠的 DSH 审批状态。先验证当前 SessionController 是否暴露稳定的待审批信号；如果没有，第一批保留“查看授权与处理详情”作为运行中辅助入口，不用关键词或超时时间伪造“正在等授权”。复用 Host 监督过程观察到的状态，不让每次页面 GET 再读取一次完整会话。

## 4. 前端组件与改动位置

在 `client.js` 内先保持当前模块加载方式，不引入新的前端构建链。

| 组件 / 位置 | 职责 |
| --- | --- |
| PersonalManagerPage | 保留项目身份、轮询、草稿、mutation 和恢复机制；根据模式装配布局 |
| ManagerModeSwitch | 简洁 / 完整管家切换；详细工作区入口保留在更多选项 |
| ManagerActionCard | 展示 `presentation`，分派固定白名单的客户端动作 |
| ManagerConversation | 复用结构化消息与输入框，避免另一套消息解析器 |
| ManagerQuestionCard | 一次一个当前问题，允许选项、自由回答和“请解释一下” |
| ManagerReviewSheet | 完整文档、重点提示、意见与明确的当前版本确认 |
| ManagerDeliverablesSheet | 单份文档和已确认包下载；高级导出折叠 |
| ManagerAdvancedPanel | 复用 TemplatePanel、来源检查及详细工作区导航 |
| ManagerHelp | 场景相关的使用说明与完整手册入口 |

前端对未知的 `presentation.schemaVersion` 或动作 `kind` 不发起请求，退回完整管家。简洁模式开关按浏览器记忆，用户的当前选择优先于默认值；切换不清空未发送消息和未提交的审阅意见。

建议新模块 `manager-presentation.js` 实现派生逻辑，并加入 `package.json` 文件清单和语法检查。`manager-message.js` 继续负责消息协议，`manager-adapter.js` 继续适配会话，`delivery-plan.js` 继续执行已确认来源校验，避免职责混在前端卡片中。

## 5. 把第一次创建项目变成两步

第一步只问“想解决什么问题”；项目名可由用户填写，或给出可编辑的建议，不要求技术选型。

第二步明确“希望先拿到什么”：

| 用户看到的选项 | 现有交付约定 |
| --- | --- |
| 先把需求写清楚 | requirements |
| 给我一份能照着做的方案 | design |
| 帮我做出可以使用的东西 | software |

用途（毕业设计、产品开发、概念演示）作为可选补充，不再由用途静默决定用户必须完成全部开发流程。用户确认后才调用已有 `configure`，明确显示本次成果范围。

旧项目沿用已有 `contract.mode`。不能把旧项目自动降级为“只做文档”。涉及扩大既有交付范围时，仍按当前服务端允许的扩展路径提出安排并等待点击；不得通过改界面状态绕过原有约定变更限制。

## 6. 保留文档，简化审阅

成果卡先用三句话说明“准备了什么 / 希望你看哪里 / 还有哪些缺口”，然后提供查看完整文档的入口。未经过验证的模型摘要明确是阅读提示，正式内容以文件为准。

审阅仍采用两步：打开并阅读 → 用户明确勾选并确认。主要按钮“查看并确认成果”只能打开审阅，不能直接确认。实现检查项、未解决评论、源文件哈希和版本变化检查继续由现有逻辑校验。

不满意时提供“告诉管家哪里需要改”。已确认内容的修改仍走 `revise` 并解释受影响的后续确认；不在后台偷偷覆盖已确认文件。普通对话不能被视作 `approve`。

长文在独立阅读面板展示，窄屏时占满内容区；提供返回对话与保留阅读位置。不能只保留摘要而取消完整文档和下载。

## 7. 把常用下载与高级导出分开

- 已存在的文档直接提供下载，不强迫普通用户先选择模板。
- “下载文档包”先检查是否已经有对应当前确认状态的包；没有时明确显示“整理文档包”，完成后再显示下载。
- “更多格式”里再提供 PDF、演示文稿和上传模板，调用现有预检 / 生成接口，不另写一套宽松的生成逻辑。
- 内容缺口用“缺什么 / 从哪里补 / 下一步做什么”表达。来源歧义必须等待用户选择，不能为了减少点击而默认选第一份。
- 标记草稿是独立、明确的选择；不能在正式生成失败后静默输出草稿并提示已完成。
- 继续显示 Word 版式、中文字体、PPTX 模板能力和文档 ZIP 不含代码 / 环境的边界。

## 8. 权限、竞态与异常

保持 `requestId` 去重、当前 `revision`、串行锁和项目 / 轮次身份检查。动作卡携带的 revision 只用于检测过期，不能成为执行权限。

服务端仍逐项验证当前约定、proposal、阶段、确认状态和文件哈希。用户在旧卡片上点击时，拒绝过期动作、刷新卡片并保留草稿；不自动把旧意图替换成新 proposal 后执行。

按钮禁用沿用已有具体 toast；原因应说明最先需要完成的一步。键盘、读屏、对比度和重复点击保护保留。Host 重启、断网及任务待核对状态不触发自动 dispatch。

不修改现有业务 Agent 的插件保护原则，不新增自动工具审批、发布、付费或外部部署授权。

## 9. 按三个批次交付

### 第一批：日常首页与真实动作卡

工作：增加 presentation 派生逻辑与协议；实现简洁首页、固定动作白名单、模式切换、当前问题和可靠的进度 / 恢复提示。现有完整管家可随时返回。

验收：每个主要状态恰好有一个主操作；运行、停止和待核对时不出现重复开始；切换模式不丢消息；当前问题不会混入旧阶段问题；未知协议安全回退。更新主手册与首页 / 沟通截图。

### 第二批：成果阅读与交付

工作：独立阅读面板、三句成果提示、修改与明确确认、常用下载、折叠高级导出、使用手册入口。

验收：看摘要不会确认文档；文件变化拒绝旧确认；未完成实现检查不能确认；直接下载不要求模板；高级导出继续拦截内容缺口；确认后的修改可追溯。更新审阅 / 导出 / 打包手册和截图。

### 第三批：首次引导、可用性验证与默认切换

工作：两步创建、明确交付范围、术语与提示文案整理、窄屏和无障碍检查；完成新手任务验证后才将简洁模式设为默认。

验收：旧项目不变更约定；首次用户能建立项目、说明需求、同意一项安排、提出修改并下载成果。更新首屏手册和完整离线版。

前两批先允许显式选择简洁模式，保留回退开关；第三批验证通过再改变默认入口。每批独立提交、独立验证，不依赖一次大改才能运行。

## 10. 验证与发布检查

自动检查应覆盖派生状态优先级、任务与问题归属、动作枚举、过期建议、重复提交、服务断连、只打开不确认、哈希变化、缺口检查及旧版数据兼容。已有测试继续保留，不用固定文本断言代替业务行为验证。

浏览器检查覆盖桌面与窄屏，使用虚构项目。涉及真实模型的验收与界面模拟验证分开记录。只在确有必要时使用用户已经授权的模型服务，不把截图中的模拟状态说成真实执行完成。

建议安排 3–5 位不熟悉开发流程的试用者完成同一组任务，记录需要别人帮助的次数、错误点击、误解确认的情况和完成时间。试用招募与消息发送另行由用户安排，本方案不自动联系任何人。目标是用户无需知道“五个阶段对应五个角色”即可完成任务，不把主观满意度当成功能正确的证据。

每批发布前：执行相关测试和语法检查；同步主手册维护记录与受影响截图；运行 `npm run docs:guide` 重建离线版，核对链接及打包清单。遵循根目录 `AGENTS.md`，不能先发布界面、以后补使用手册。

## 11. 当前与未来的界线

本次仅交付实现方案。1.14.1 已有结构化回复、禁用提示、文档版本确认、模板预检和 PDF / PPTX 输出；本方案中的简洁首页、统一动作卡、两步引导、独立阅读面板和内置手册入口尚未实现。
